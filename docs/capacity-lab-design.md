# 容量実験 Web アプリ（caplab）設計

テーブル定義・クエリ・頻度を登録すると、**MySQL の CPU 負担と接続数を試算**し、同じ定義で**実際に負荷をかけて測り、試算と突き合わせる**アプリ。
きっかけは [tenant-cpu-isolation](tenant-cpu-isolation.md)（EXP-65）。あそこで手作業だった「ワーカー・Web・認証を混ぜた上限の見積り」をアプリにする。

## 言語の選択（Rust）

- 決め手: 負荷生成を軽く保てる（GC が無い・メモリが小さい）こと、ゴールが固まっていて仕様の変更が少ないこと、型で定義の誤りを実行前に落とせること。
- **Go の資産の扱い**: `internal/expkit` は Go のため、必要な部分を Rust に移植する。
  - `Latency`（分位点）→ `hdrhistogram`。`Env`（測定条件の採取）→ 移植（Rust の版・OS・CPU・MySQL 変数・git SHA）。`Recorder`（JSON + Markdown 保存）→ 移植。
  - `internal/lint`（テナント条件の検査）→ `sqlparser` で書き直す。Go 側の `cmd/sqllint` と**同じテストケース**を共有して、判定が一致することを確かめる。
  - `Sampler`（接続プール・メモリの時系列）は、Rust 側では MySQL の `SHOW GLOBAL STATUS` とプロセスのメモリ採取で作り直す。
- 負荷側のスケジュール遅れを必ず記録する方針は変えない（言語を問わず、負荷側の詰まりを見つけるため）。
- 「軽い」という利点は、**この環境では未測定**。M3 で負荷側の CPU を実測し、設計書の前提（負荷側は DB より十分軽い）が成り立つかを確かめる。

## 対応エンジン（MySQL と PostgreSQL の両方）

同じワークロード定義を、**エンジンを切り替えて試算・実行・比較できる**ようにする。EXP-65 の実測は PostgreSQL、運用先は MySQL なので、
両方で測れること自体に価値がある（同じ定義で「エンジンによる差」が見える）。

エンジンの違いは `Engine` トレイトに閉じ込める:

| 差分 | MySQL | PostgreSQL | `Engine` が吸収すること |
| --- | --- | --- | --- |
| 接続 | 接続ごとにスレッド | 接続ごとにプロセス（アイドル接続のコストが重い） | アイドル接続のコストは**エンジンごとに別測定**（相互に流用しない） |
| 状態の採取 | `SHOW GLOBAL STATUS`（`Threads_connected` / `Threads_running`）、`performance_schema` | `pg_stat_activity`、`pg_stat_database`、`pg_stat_statements`（拡張が必要） | `snapshot()` が共通の項目（接続数・実行中数・読み取り行数）に正規化 |
| クエリ別の CPU | `performance_schema` の `SUM_CPU_TIME`（8.0.28+、要検証） | `pg_stat_statements` は実行時間のみで **CPU 時間は無い** | クエリ別 CPU は MySQL のみ。PostgreSQL は**校正（単体実行の cgroup 差分）**で出す |
| DB 全体の CPU | cgroup / docker / CloudWatch | 同左（EXP-65 で cgroup を使用済み） | `cpusrc` は共通 |
| プレースホルダ | `?` | `$1` | 定義は `:name` で書き、`Engine` が変換 |
| DDL・型・関数 | `AUTO_INCREMENT`、`DATETIME` など | `SERIAL` / `IDENTITY`、`TIMESTAMPTZ` など | クエリ・DDL は**エンジンごとに上書き可能**（`sql: {"mysql": …, "postgres": …}`）。共通の SQL で動く間は 1 つで足りる |
| 実行計画 | `EXPLAIN ANALYZE`（8.0.18+） | `EXPLAIN (ANALYZE, BUFFERS)` | 計画の文字列を保存し、読み取り行数だけ共通項目に抜く |
| 送信方式 | テキスト / プリペアド | simple / extended | `protocol: text | prepared` を定義に持つ（本物のアプリに合わせる） |
| プロキシ | RDS Proxy（ピン留めの規則はエンジンで異なる） | 同左 | 接続モデルに `proxy` を持つが、ピン留めの規則は**エンジンごとに別途確認** |

- ドライバは `mysql_async` と `tokio-postgres` を `Engine` の後ろに置く（`sqlx` の `Any` は機能が限られるため使わない）。
- プロファイルに `engine` を持たせる（`{"name": "pg-2vcpu", "engine": "postgres", "vcpu": 2, …}`）。校正表・膝の位置は**プロファイル（エンジン × vCPU）ごと**。
- 比較画面は「同じワークロード × エンジン違い」を並べられるようにする。スキーマはエンジンごとの DDL が要るので、最初は共通の簡単な型だけで始める。
- **M0 の確認はこの環境の PostgreSQL 16 でできる**（MySQL は無い）。MySQL 側の確認はユーザーの環境で行う。

## 接続の 3 層の観察（アプリ → Proxy → DB）

接続数を 1 つの数字で扱わず、**3 層に分けて同時に採取・表示**する。実測の例は [proxy-connection-layers](proxy-connection-layers.md)。

| 層 | 意味 | 取得（`ProxyObserver`） |
| --- | --- | --- |
| ① アプリ → Proxy | アプリのプールが張る接続（コンテナ数 × プール上限が上限） | PgBouncer `SHOW LISTS` / ProxySQL `stats_mysql_global` / CloudWatch `ClientConnections` |
| ② Proxy → DB | 実際に DB へ張られた接続。待たされているクライアントの数も見る | PgBouncer `SHOW POOLS` / ProxySQL `stats_mysql_connection_pool` / CloudWatch `DatabaseConnections` など |
| ③ DB 側 | DB から見た接続数と、実行中の数 | `pg_stat_activity` / `SHOW GLOBAL STATUS`（`Threads_connected`・`Threads_running`） |

- プロファイルに `proxy: {kind: "none" | "pgbouncer" | "proxysql" | "rds_proxy", pool_mode, pool_size, …}` を持たせる。
  ローカルは PgBouncer（PostgreSQL）と ProxySQL（MySQL）が RDS Proxy の代用品。**ピン留めの規則は RDS Proxy と異なる**旨を画面に常に出す。
- 試算の接続モデルは `DB 実接続 ≈ min(プール上限, 同時に必要な接続数)`、同時に必要な接続数 = `トランザクション/秒 × トランザクションの保持時間`。
  保持時間にアプリの外部待ちが入ると跳ね上がり、プール上限に当たる（実測: 500/秒 × 50ms = 25 本必要、プール 10 で p95 が 7 秒）。
- 「DB の CPU が低いのに遅い」を検出するため、**待たされているクライアント数（`cl_waiting`）と、CPU 使用率を同じグラフに出す**。

## 目的と、やらないこと

| やる | やらない |
| --- | --- |
| 登録したワークロードの CPU 使用率・接続数の試算 | 本番 DB への接続（ガードで拒否） |
| 同じ定義の実行（負荷生成・計測） | 本番の SQL の自動収集（まず手で登録。収集は後段） |
| 試算と実測の差の表示（試算の信用度を知る） | DDL / DML の自動最適化提案 |
| テナント数の掃引と、限界点（膝）の自動探索 | MySQL / PostgreSQL 以外のエンジン（Aurora など MySQL / PostgreSQL 互換は同じ `Engine` で扱う） |

## EXP-65 から設計に入れた教訓

1. **1 クエリの CPU はクライアント数で変わる**（同じクエリが 0.42ms ↔ 0.77ms）。単一の「ms/回」を持たず、**同時接続数ごとの校正表**を持つ。
2. **試算は線形、実機は 88% 付近で曲がる**。試算は線形で出し、**膝の位置は実測の掃引から出す**。線形値だけを安全値として見せない。
3. **開ループ（到着率固定）で測る**。待ち行列を含めて遅延を測るため、遅延は「予定時刻」から数える（pgbench `-R` と同じ）。
4. **時刻をそろえると山ができる**。ワーカーの起動を `揃える / ずらす` で切り替えて比べられるようにする。
5. **測定条件を必ず残す**（`expkit.Env`）。絶対値はマシンで変わる、が前提。

## 構成

```
ブラウザ (SPA)  ──JSON──  caplab (Rust, 単一バイナリ, 静的ファイル埋め込み)
                           ├─ model      プロジェクト定義（スキーマ・クエリ・アクター）
                           ├─ schema     DDL 取り込み・データ生成
                           ├─ calib      クエリ単体の校正（CPU/回 × 同時数）
                           ├─ estimate   試算（CPU・接続数・安全上限）
                           ├─ runner     負荷実行（開ループ・直列ステップ・テナント掃引）
                           ├─ dbstat     MySQL の状態採取（接続・実行行数）
                           ├─ cpusrc     CPU 採取のプラグイン（下記）
                           ├─ guard      実行先・SQL の安全確認
                           └─ store      プロジェクト JSON と実行結果の保存
                                │
                                ▼
                       実験用 MySQL（ラボ専用。例: docker compose の mysql:8.0 に --cpus=2）
```

- **言語は Rust**（理由は下の「言語の選択」）。リポジトリ内の置き場は `caplab/`（独立した Cargo ワークスペース。Go のモジュールとは混ぜない）。
- 主な crate（案）: `tokio`（非同期・タイマー）、`axum`（API と SSE）、`mysql_async`（MySQL。`sqlx` でもよい）、`serde` / `serde_json`、`rust-embed`（静的ファイル同梱）、`sqlparser`（SQL の解析）、`hdrhistogram`（遅延の分位点）、`clap`。
- 下のパッケージ名（`model`・`estimate` など）は、Rust ではモジュール名（`src/model.rs` …）に読み替える。
- 定義は **1 プロジェクト = 1 つの JSON ファイル**（git に入れられる）。実行結果は `runs/<時刻>/` に JSON + Markdown で保存する。DB は持たない。

## データモデル（プロジェクト JSON）

```jsonc
{
  "name": "site-monitor",
  "profiles": [                       // DB スペックの候補。画面で切り替え・並べて比較できる
    {"name": "2vcpu", "engine": "mysql", "vcpu": 2, "memory_gb": 8,  "max_connections": 200, "dsn_env": "CAPLAB_DSN_2"},
    {"name": "4vcpu", "engine": "mysql", "vcpu": 4, "memory_gb": 16, "max_connections": 400, "dsn_env": "CAPLAB_DSN_4"}
  ],
  "active_profile": "2vcpu",
  "tenants": {"count": 300, "boundary_column": "tenant_id"},
  "schema": {
    "ddl": ["CREATE TABLE sites(...)", "..."],
    "tables": [{"name": "devices", "rows_per_tenant": 100,
                "columns": {"status": {"gen": "enum", "values": ["ok","ng"]},
                            "id": {"gen": "seq"}}}]
  },
  "queries": {
    "poll_devices": {"sql": "SELECT ... WHERE tenant_id = :tenant AND id > :after",
                      "params": {"tenant": "tenant", "after": {"gen": "int", "min": 0, "max": 100}}}
  },
  "actors": [
    {"kind": "worker", "name": "sync-1s", "every": "1s", "per": "tenant",
     "stagger": true, "pool": {"max_open": 4, "max_idle": 4},
     "steps": [{"query": "poll_devices"}, {"query": "poll_devices"}, ...]},   // 直列 6 回なら 6 行
    {"kind": "web", "name": "api-list", "rate": {"per": "tenant", "qps": 1.2},
     "pool": {"max_open": 20}, "steps": [{"query": "auth_session"}, {"query": "list_devices"}]},   // 1 リクエスト = 1 ループ分のクエリ
    {"kind": "batch", "name": "monthly-report", "schedule": {"every": "60s", "concurrency": 2},
     "scope": "tenant_range", "tenants": [1, 50],        // 重いバッチ: 複数テナント分をまとめて集計など
     "pool": {"max_open": 2}, "steps": [{"query": "report_agg"}]}
  ]
}
```

- **ステップは順序つきの配列**。「1 秒に直列 6 回」は 6 要素（同じクエリを繰り返してもよい。`{"query": "x", "repeat": 6}` の省略記法も許す）。
- **Batch（重いバッチ）**は、`schedule`（`every` の定期実行 / `once` の 1 回きり / `continuous` の流しっぱなし）と `concurrency`（同時に何本流すか）を持つ。
  対象は `tenant`（1 テナント分）か `tenant_range`（複数テナント分をまとめて）。通常のワーカー・Web と**同じ DB で同時に動かして影響を見る**（実験: 50 テナント分の集計を流すと全体の p95 が 3.3 → 12.9ms）。
  バッチだけを別プロファイル（別 DB / レプリカ）に向ける設定も持てる（隔離した場合の比較）。
- **Worker**は `every`（間隔）× `per`（`tenant` ごと / `global`）で頻度を決める。`instances`（同じワーカーを何本動かすか）も持つ。
- **Web** は `rate`（`per: tenant | user`、`qps`）。`per: user` のときは `users_per_tenant` を掛ける。API ごとに 1 アクターを登録する。
- 認証クエリは、ふつうのクエリとして Web アクターのステップの先頭に置く（キャッシュ率は `cache_hit` で表す。例: `{"query":"auth","cache_hit":0.98}`）。
- **SSE** は `connections_per_tenant` と、接続時に流す初期クエリ（`on_connect` ステップ）だけを持つ。配信は DB を引かない前提（hub 方式）。
- クエリの `params` はジェネレータ名か、`tenant`（現在のテナント ID）、`sample(table.column)`（実データから抽出）。

## かんたんスキーマ（親・子・孫のテーブルを画面で作る）

DDL を書かなくても、画面でテーブルの形を決めて生成できる（DDL の取り込みも併用できる）。**値の中身は決めず、サイズと件数だけ**を指定する。

| 指定する項目 | 内容 |
| --- | --- |
| 親子関係 | 親 → 子 → 孫（1 対多）。各テーブルに「親 1 件あたりの子の件数」を指定する |
| 件数 | 親は「1 テナントあたり N 件」。子・孫は「親 1 件あたり M 件」（例: 親 100 件 × 子 10 件 = 1,000 件）。絶対件数で指定しても良い |
| カラム数 | テーブルごとに指定（主キー・親への外部キー・`tenant_id` は自動で付くので、それ以外の数） |
| 型 | 標準的な型（整数・文字列・日時・小数・真偽・長い文字列）を**システムが適当に混ぜて割り当てる**。ユーザーは型を選ばない |
| 行のサイズ | 大・中・小から選ぶ。小 ≈ 100 B / 行、中 ≈ 1 KB / 行、大 ≈ 10 KB / 行（長い文字列・JSON 相当を含む）。生成後に実測のサイズを表示する |
| 値 | システムが決める（乱数、親子の整合は保つ）。分布は一様。値の具体は指定できない |
| インデックス | 主キーと、親への外部キーに付ける（切り替え可能。**外しておくと遅くなる実験**ができる） |

- すべてのテーブルに `tenant_id` を自動で付け、主キーは `(tenant_id, id)`、子の外部キーは `(tenant_id, 親id)`（テナントが境界）。
- 画面は MySQL / PostgreSQL のどちらの DDL も自動で作る（型の対応表はエンジンごとに持つ）。生成した DDL は確認・編集できる。
- 例: `sites`（親・中）→ `devices`（子・小・親 1 件あたり 10 件）→ `readings`（孫・小・子 1 件あたり 20 件）。

## クエリフロー（親 → 子 → 孫）

「1 回のループで、複数のクエリが、前のクエリの結果に応じて動く」ことを、**フロー図**で登録する。ここがいちばん分かりにくいので、
画面は**実行回数を数字で見せる**。

1. **親のクエリ**を 1 回実行する（例: サイトを 1 件取る）。
2. その結果を使って**子のクエリ**を実行する（例: そのサイトの機器を取る）。
3. 子の結果の**各行**について**孫のクエリ**を実行する（例: 機器ごとに測定値を取る）。ここが「ループ」。

```
親  SELECT … FROM sites   WHERE id = :site                 1 回   → 1 行
 └ 子  SELECT … FROM devices WHERE site_id = :親.id         1 回   → 10 行
     └ 孫  SELECT … FROM readings WHERE device_id = :子.id   10 回（子の行ごと） ← ループ
                                          1 ループ = 1 + 1 + 10 = 12 クエリ
```

- ステップの設定は 3 つだけ: **クエリ**、**いつ実行するか**（「1 回」/「前の結果の各行について」）、**ループの上限**（前の結果の最大 N 行まで）。
- 実行回数は `親の回数 × 子の行数 × …` で増える（**N+1**）。画面は「1 ループあたり 12 クエリ（推定）」を常に表示し、実際の行数から計算し直す。
- 定義の書き方（JSON）:

```jsonc
"steps": [
  {"id": "p", "query": "get_site"},
  {"id": "c", "query": "list_devices",  "params": {"site_id": "$p.id"}},
  {"id": "g", "query": "list_readings", "params": {"device_id": "$c.id"},
   "foreach": "c", "limit": 20}          // c の各行について実行（最大 20 行まで）
]
```

- **同じ結果を取る別の書き方と比べられる**ようにする（登録は 1 つのテンプレートで切り替え）:

| 形 | クエリ数/ループ | 1 クエリの重さ | 試す意味 |
| --- | --- | --- | --- |
| 親 → 子 → 孫（N+1） | 多い（12 など） | 軽い | DB との往復回数が増える |
| JOIN で一括 | 1 | 重い（結果が大きい） | 往復を減らす代わりに 1 回が重くなる |
| `IN (…)` でまとめる | 3（親・子・孫まとめて） | 中 | 往復と重さの中間 |

  往復が増えるコストは、ネットワーク遅延（実環境）で効くため、**ローカルでは過小評価になる**旨を画面に出す。CPU の負荷は測れる。

## DB スペックの切り替え（2 vCPU → 4 vCPU など）

スペックは**プロジェクトに固定せず `profiles` として持ち**、画面の切り替えで試算・実行の前提を変える。同じワークロードを 2 つ以上のプロファイルで並べて比較できる（「4 vCPU にすると上限は何テナントか」）。

| 項目 | 切り替えで変わるか | 扱い |
| --- | --- | --- |
| `vcpu` | 変わる | 試算の分母。実行時は CPU 上限（cgroup quota / `docker --cpus`）の指示にも使う |
| `max_connections` | 変わる | 接続の予算（予約を引く）。RDS ならメモリから決まる既定式を選べる |
| `memory_gb`（バッファプール） | 変わる | **試算では使わず、警告のみ**（データ量 > バッファプールなら「ディスク読みが出る」と注意）。効果の見積りは未対応 |
| `cpu_ms/回`（校正表） | **ほぼ変わらないが保証されない** | プロファイルごとに持つ。別プロファイルの校正値を流用するときは「流用」と表示する |
| 悪化開始・崩壊の使用率（膝） | **変わりうる** | プロファイルごとに掃引で測る。**無ければ既定値（60/88/95%）に「2 vCPU の実測の流用」と注記** |
| 安全使用率・予約 vCPU | 変わる | プロファイルごとに設定。予約は固定値（0.1 vCPU）なので、vCPU が増えるほど割合は小さくなる |

- **試算は vCPU に対して線形**に出す（CPU 合計 ÷ vCPU）。ただし 4 vCPU で 2 倍の上限になるとは**限らない**。
  実際には、同時実行が増えるぶんロック競合・コンテキストスイッチ・バッファプールの競合で CPU/回が増える
  可能性がある（EXP-65 で同時数により 0.42 ↔ 0.77ms と変わった）。そのため、**試算の画面は「線形の値」と
  「そのプロファイルで校正・掃引した値」を区別して表示**し、後者が無いプロファイルには「未検証」を付ける。
- **実行は、実際に 4 vCPU の DB に向けて測る**のが唯一の確認方法。ローカルなら `docker --cpus=4`（または cgroup quota 4000m）、
  RDS なら該当インスタンスクラスの DB を指す。負荷側は DB と別のコア / ホストにする（4 vCPU の DB を測るなら、負荷側は 4 コア以上要る場合がある。
  アプリがスケジュール遅れを見て「負荷側が詰まっている」と警告する）。
- **プロファイル間の比較画面**: 同じテナント数で、vCPU ごとの使用率・p95・安全上限を並べる。
  「2 vCPU の安全上限 → 4 vCPU の安全上限（試算 / 実測）」の比が、**線形からのずれ**としてそのまま見える。
- 将来 MySQL 以外・Aurora などを足すときも、`profiles` に `engine` と CPU 採取方式（`cpusrc`）を持たせるだけで済むようにする。

## 試算（`estimate`）— 実行せずに出す

入力は上の定義 + 有効なプロファイル + 校正表（下記）。出力:

**1. クエリごとの実行頻度**

```
qps(q) = Σ_actor  rate(actor) × tenants × (actor.steps の中の q の回数) × (1 − cache_hit)
rate(worker) = instances / every          rate(web) = qps / テナント（user なら × users）
```

**2. CPU**

```
cpu_vcpu(q)  = qps(q) × cpu_ms(q, c) / 1000          c = 想定同時接続数（接続数の試算から引く）
cpu_util     = Σ cpu_vcpu(q) / profile.vcpu      // 有効なプロファイルの vcpu
```

`cpu_ms(q, c)` は校正表から線形補間する（**クライアント数で変わる**ため。教訓 1）。校正が無いクエリは「未校正」と表示し、合計は幅（最小〜最大）で出す。

**3. 接続数**（リトルの法則 + プール上限）

```
同時実行(actor) ≈ min( qps(actor) × latency_wall(actor), pool.max_open × インスタンス数 )
接続合計 = Σ pool.max_open × インスタンス数   // 上限側（張りっぱなしを含む）
        vs  max_connections、予約（migration・監視など）を引いた予算
```

「上限側の接続」と「同時実行（Threads_running 相当）」を別々に出す。接続が足りなくなるのは前者、CPU が効くのは後者。

**4. 安全上限**

```
安全使用率 = 設定値（既定 60%）、非テナント処理の予約 = 設定値（既定 0.1 vCPU）
安全上限テナント数 = (vcpu × 安全使用率 − 予約) / (1 テナントあたりの cpu_vcpu)
```

結果画面は、内訳（アクター別・クエリ別の積み上げ）、使用率バー（安全 / 悪化開始 / 崩壊の目盛り。**目盛りの位置は実測の掃引結果があればそれを使い、無ければ既定の 60/88/95% と注記**）、安全上限を出す。

## 校正（`calib`）— クエリ単体のコストを測る

- 各クエリを、同時数 c ∈ {1, 4, 16, 32, 64}（設定可）で、**1 点あたり 5〜10 秒**、開ループで流し、`cpu_ms/回` と `p50/p95` を記録する。
- `EXPLAIN ANALYZE` の結果（読み取り行数・使ったインデックス）を併記し、**全表走査・テナント条件なし**を警告する（`internal/lint` を呼ぶ）。
- 校正結果はプロジェクトに保存し、スキーマやデータ量を変えたら「古い」と表示する。

## 実行（`runner`）

- 各アクターを、**テナント × インスタンス**ごとのスケジューラとして動かす。ステップは**直列**（前の完了を待つ）、起動は**開ループ**（予定時刻で発火し、遅延は予定時刻から数える）。
- `stagger: true` は起動時刻をテナントごとにずらす（一様分布）。`false` は同時起動。**同じ定義で両方を比べる**ボタンを付ける。
- 実行モード:
  - `steady`: 指定テナント数で一定時間（ウォームアップ除外）。
  - `sweep`: テナント数を段階的に上げ（例 100 → 1000）、**p95 が閾値を超える、または CPU が上限を超える最初の点を「膝」として記録して止める**。
  - `calibrate`: 上記の校正。
- 計測するもの（1 秒ごと）: クエリ別 qps・p50/p95/p99・エラー、`Threads_connected` / `Threads_running`、`Innodb_rows_read` の差分、DB の CPU（`cpusrc`）、アプリ側のスケジュール遅れ（これが大きいと負荷側が詰まっている印）。
- **負荷側の CPU を DB と分ける**（別コアに固定、または別ホスト）。同じホストなら、アプリがその旨を警告する（EXP-65 では DB をコア 0,1・負荷をコア 2,3 に固定した）。

## CPU の採取（`cpusrc` プラグイン）

| 方式 | 使える場面 | 状態 |
| --- | --- | --- |
| `cgroup` | 同一ホストで cgroup（v1 `cpuacct.usage` / v2 `cpu.stat`）が読める | EXP-65 で PostgreSQL に対して使用済み。MySQL でも同じ |
| `docker` | `docker stats` / cgroup 経由 | 未実装（環境に docker が無く未確認） |
| `performance_schema` | 接続だけで取れる。8.0.28+ の `events_statements_*` の `CPU_TIME` 列 | **要検証**（列の有無とバージョン、要約テーブルに無い点の確認が必要） |
| `cloudwatch` | RDS / Aurora の `CPUUtilization`（粒度 1 分、最大 1 秒の拡張モニタリング） | 後段。粒度が粗く校正には不向き |
| `manual` | ユーザーが値を入力 | フォールバック |

どの方式かは、結果に必ず記録する。方式によって「DB の CPU」の意味（ホスト全体 / mysqld のみ）が違うため。

## ガード（`guard`）

- 実行先は**許可リスト**（既定 `127.0.0.1` と `*.lab.*` など）。許可外のホストは実行しない。DSN は環境変数から読み、プロジェクト JSON には書かない。
- 使うスキーマ名は `caplab_` で始まるものに限る。それ以外へのクエリは拒否する。
- SQL は 1 文のみ（複数文の拒否）、既定は `SELECT` のみ。`INSERT/UPDATE/DELETE` はプロジェクトごとに明示的に許可し、実行は専用スキーマ内のみ。DDL は取り込み時の 1 回だけで、実行中は不可。
- 上限: 最大 qps・最大同時接続・最大時間をプロジェクトで設定。画面に常に「停止」を出し、停止時はすべて即時にキャンセルする。
- `tenant_id` 条件のないクエリは**警告**（実行は可能。EXP-58 の事故型。[tenant-scope](tenant-scope.md)）。

## メトリクス画面（Datadog 風ダッシュボード）

実験中も実験後も、**同じ画面で重要なメトリクスを時系列で見られる**ようにする。見る人が最初に知りたいのは
「今どこが詰まっているか（CPU / 接続 / ロック / スケジュール遅延）」なので、**飽和のシグナルを先頭に置く**。

### 収集

- コレクタが 1 秒ごと（設定可）に各層をサンプリングし、`(名前, タグ, 時刻, 値)` で記録する。タグは `run_id`・`engine`・`profile`・`actor`・`query`・`layer`。
- 遅延は**1 秒ごとの HDR ヒストグラム**で持ち、画面の集計幅に応じて**ヒストグラムを合成して**分位点を出す（p95 の平均を取らない）。
- 保存: 直近のデータはメモリのリングバッファ（1 秒粒度で 1 時間）、実行ごとに `runs/<id>/metrics.jsonl` へ追記（終了後も開ける・比較できる）。外部の時系列 DB は使わない。
- 取り込み口は `Collector` トレイト。後段で CloudWatch / Datadog の API からの取り込みを足せる（RDS の実環境と並べるため）。

### メトリクス一覧（重要なものを先頭に）

| グループ | メトリクス | 何が分かるか |
| --- | --- | --- |
| **飽和（先頭）** | DB の CPU 使用率（安全 / 悪化開始 / 崩壊の目盛り）、CPU スロットル回数、Proxy の待機クライアント数、アプリのプール待ち回数、スケジュール遅延、`Threads_running`（MySQL）/ `active` 数（PostgreSQL） | どの限界に最初に当たっているか |
| 負荷 | 予定 qps と達成 qps、アクター別 qps、エラー率 | 負荷が計画どおり出ているか。達成が足りなければ負荷側 / DB が詰まっている |
| 遅延 | p50 / p95 / p99、アクター別・クエリ別、分布のヒートマップ | 遅延の悪化の始まりと裾 |
| 接続 3 層 | ① アプリのプール（open / in-use / idle / 待ち回数 / 待ち時間）、② Proxy（クライアント数・サーバ接続数・待機数）、③ DB（接続数・実行中数） | 接続が増えても DB 接続がどう動くか。**3 層を 1 つのグラフに重ねる** |
| DB 内部 | 読み取り行数/秒、ロック待ち、デッドロック、バッファプールのヒット率、一時テーブル（MySQL） | CPU の原因の切り分け（JOIN か、大量実行か、ロックか） |
| クエリ別 | CPU 時間の上位、実行回数、平均 / 最大時間（MySQL: `performance_schema`、PostgreSQL: `pg_stat_statements`） | どの SQL が重いか |
| 負荷側 | 負荷生成の CPU・メモリ、スケジュール遅延 | **測定が信用できるか**（負荷側が詰まっていないか） |

### 画面

```
┌─ 実験: 接続プール枯渇 ─ run #12 ─ [ライブ ▶] [過去 15分 ▾] ─ engine:[mysql ▾] profile:[2vcpu ▾] ─ ⚠ 警告 2 ┐
│ ┌ 飽和ボード ───────────────────────────────────────────────────────────────────────────────┐ │
│ │ CPU 47% [■■■■□□□□□□]   待機 90 ⚠   プール待ち 1.2k ⚠   スケジュール遅延 p99 18ms   接続 11/200   │ │
│ └────────────────────────────────────────────────────────────────────────────────────────────┘ │
│ ┌ DB の CPU と スロットル ┐ ┌ 接続の 3 層（アプリ / Proxy→DB / DB 実行中） ┐ ┌ p50 / p95 / p99 ┐ │
│ │ ──── 60% 88% 95% の線   │ │ ▁▂▃▅▇ アプリ 100 ▁▁▁ Proxy→DB 10 ▁ 待機 90 │ │ ヒートマップ     │ │
│ └─────────────────────────┘ └──────────────────────────────────────────┘ └──────────────────┘ │
│ ┌ アクター別 qps（積み上げ） ┐ ┌ クエリ別 CPU 上位 ┐ ┌ スケジュール遅延 ┐ ┌ ロック待ち / 行読み取り ┐ │
│ 縦の印: ▲ 実行開始  ▲ 起動を「ずらす」に切替  ▲ プール 10→40                                        │
└────────────────────────────────────────────────────────────────────────────────────────────────┘
```

- **共有クロスヘア**: 1 つのグラフにカーソルを置くと、全パネルが同じ時刻の値を表示する。
- **時間範囲**: ライブ（直近 N 分）/ 過去の実行を選択 / ドラッグで拡大。
- **タグで絞り込み・グループ分け**: アクター、クエリ、エンジン、プロファイルで切り替える（Datadog の `group by`）。
- **しきい値**: CPU の 60 / 88 / 95% の線を常に描く（実測の掃引結果があればそれに差し替え）。警告は上部のバナーに出す。
- **イベントの印**: 実行の開始・停止、設定変更（プール値、ずらす / 揃える、プロファイルの切替）を縦線で重ねる。**何を変えたらどう変わったか**が読める。
- **2 つの実行の重ね合わせ**: 実行 A と B を同じ時間軸に揃えて重ねる（直結と Proxy 経由、ずらすと揃える、2 vCPU と 4 vCPU）。
- **プリセットのダッシュボード**: 概要 / 接続の 3 層 / クエリ別 / ワーカーのスケジュール。ダッシュボードの定義は JSON で保存・共有できる。
- **警告ルール**（初期値）: CPU > 60%、待機クライアント > 0 が 10 秒継続、スケジュール遅延 p99 > 1 秒、負荷側 CPU > 80%（測定が信用できない）。

### 実験のプリセット（ボタンで実行）

| プリセット | 内容 | 画面で見るもの |
| --- | --- | --- |
| 接続数の掃引 | アプリ接続を 10 → 100 → 400 と上げる（直結と Proxy 経由） | 3 層の接続数と CPU |
| プール枯渇 | トランザクション内の外部待ち（50ms など）を入れ、プールを変える | 待機数・p95・CPU の乖離（CPU が低いのに遅い） |
| 起動タイミング | 全サイト同時起動とずらし起動を同じ負荷で比べる | スケジュール遅延・p99・プール待ち |
| テナント数の掃引 | N を上げて膝を探す | CPU・p95・安全上限 |
| vCPU / エンジン比較 | 同じワークロードを 2 vCPU と 4 vCPU、MySQL と PostgreSQL で | 2 つの実行の重ね合わせ |

プリセットは「準備（データ・プロキシ・プロファイル）→ 実行 → 比較用の保存」までを 1 つの定義で持つ。ローカルでは PgBouncer / ProxySQL が Proxy の代わりになる（ピン留めの規則は RDS Proxy と異なる旨を画面に出す）。

### 実装方針

- API: `GET /api/metrics/query?name=…&tags=…&from=…&to=…&step=…&agg=…&group_by=…`（Datadog のクエリに近い形）、ライブ更新は SSE `GET /api/metrics/stream`。
- 画面: ビルド手順を持たない素の ES モジュール + 描画ライブラリ（候補は `uPlot`。軽量で時系列に強い）。ライブラリは**リポジトリ内に同梱**して CDN に依存しない。ヒートマップは canvas で自前描画。`rust-embed` で同梱する。
- 重い集計（ヒストグラム合成、ダウンサンプリング）はサーバ側で行い、ブラウザには描画に必要な点だけを送る（1 パネル最大 ~1,000 点）。

## テスト方針

- **試算の受け入れテスト**: EXP-65 の記録（`docs/results/tenant-cpu-lab/*.tsv`、1 クエリ 0.74〜0.77ms、2,000 テナントで使用率 75〜80%）から作ったプロジェクトを試算して、実測の ±15% 以内に収まる。
- 純粋関数（試算・リトルの法則・補間）は表駆動テスト。DB なしで動く。
- 実行系は実 MySQL に対する統合テスト（既存の `mysqltest` を使う）。ガードは「拒否されること」を必ず検証する。
- UI は Playwright で、定義 → 試算 → 小さな実行 → 比較の一連を 1 本通す。

## 未確認・要判断

- **MySQL をこの環境で動かせていない**（docker も mysqld も無い）。EXP-65 の実測はすべて PostgreSQL。MySQL での CPU/回、`CPU_TIME` 列の有無、cgroup での採取は**ユーザーの環境で最初に確認する**。PostgreSQL 側の確認はこの環境でできる。
- Datadog で見た「接続数 100 超」が、アプリ→Proxy か Proxy→DB か**は未確認**（ユーザーが確認する）。接続の実験の優先順位が変わる。
- 実行先 MySQL をどこで動かすか（ローカルの docker compose を想定。RDS を直接測る場合は CPU の採取方法が変わる）。
- 試算が実測から外れる要因（ロック競合・バッファプールのヒット率・データ分布の偏り）は、線形モデルでは表せない。**差が大きいときは「試算を信用しない」ことを画面が示す**設計にする。
- 認証の実クエリ・Web の実クエリは、ユーザーが登録するまで仮のものしか無い。
- **4 vCPU の実測はまだ無い。** 4 vCPU での膝の位置・CPU/回は、実際に 4 vCPU の DB を測るまで分からない（線形の試算は出せる）。
