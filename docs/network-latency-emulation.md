# ネットワーク遅延の演出（中間サーバ）— 試作と限界

ECS → RDS Proxy → Aurora 間の実際の遅延を、**中間の TCP サーバで演出**できるかを試した。
試作は [scripts/tenant-cpu-lab/delayproxy.py](../scripts/tenant-cpu-lab/delayproxy.py)、測定は [net.sh](../scripts/tenant-cpu-lab/net.sh)、
生データは [docs/results/tenant-cpu-lab/net.tsv](results/tenant-cpu-lab/net.tsv)。PostgreSQL 16（2000m）、クライアント 4 本（閉ループ）、各 10 秒・1 回。

## 測ったこと

1 ループ = **直列 12 クエリ**（親 1 + 子 1 + 孫 10 の N+1 型）。中間サーバが方向ごとに遅延（片方向 = RTT ÷ 2）を入れる。

| 設定した RTT (ms) | 1 ループの平均 (ms) | ループ/秒 | クエリ/秒 | DB の CPU |
| --- | --- | --- | --- | --- |
| 0（直結） | 1.4 | 2,897 | 34,762 | 196% |
| 0.05 | 4.1 | 974 | 11,689 | 72% |
| 0.5 | 33.0 | 121 | 1,454 | 23% |
| 1 | 36.8 | 109 | 1,306 | 22% |
| 2 | 38.5 | 104 | 1,247 | 21% |
| 5 | 87.1 | 46 | 551 | 11% |

## 分かったこと

1. **遅延は DB の CPU をほとんど使わず、1 ループの時間とクライアントの占有時間を伸ばす。** 閉ループの 4 クライアントでは、RTT が大きいほど DB の CPU が下がる（196% → 11%）。
   DB が楽になったのではなく、**クライアントが往復を待って DB に仕事を渡せていない**。
2. **1 ループの時間はほぼ `クエリ数 × (RTT + 実行時間)`。** N+1 の 12 クエリは RTT の 12 倍がそのまま効く。
   RTT 5ms なら 1 ループ 60ms 以上（実測 87ms）。JOIN で 1 クエリにすれば往復は 1 回。**ローカルの直結では N+1 の損が見えない**理由。
3. **接続の占有時間が伸びる → 必要な接続数が増える。** 1 ループの間は同じ接続を使い続けるため、リトルの法則で
   `必要な接続数 ≈ ループ/秒 × 1 ループの時間`。RTT 5ms・1,000 ループ/秒なら約 87 本（実測の 87.1ms から）。プールや Proxy の上限に近づく（[proxy-connection-layers](proxy-connection-layers.md) の枯渇と同じ形）。

## 試作の限界（重要）

**この試作は、RTT 数 ms 以下の遅延を正確に再現できない。** 理論値（`12 × RTT` ＋ 直結の実行時間）と実測の差を 1 クエリあたりにすると:

| RTT (ms) | 実測 − 12×RTT（1 ループ, ms） | 1 クエリあたりの余計な遅延 (ms) |
| --- | --- | --- |
| 0.05 | 3.5 | 0.29 |
| 0.5 | 27.0 | 2.25 |
| 1 | 24.8 | 2.07 |
| 2 | 14.5 | 1.21 |
| 5 | 27.1 | 2.26 |

- 遅延を入れると、**1 往復あたり約 2ms の余計な遅延**が乗る。原因はタイマーの刻み（Python の asyncio は約 1ms 単位で待つため、片方向ごとに切り上がる）と推測。**未切り分け**。
- 同一 AZ 内の RTT は一般に 1ms を大きく下回る（要実測）。この領域は、**アプリ内のタイマー式の中間サーバでは演出できない**。
  Rust の `tokio` のタイマーも約 1ms 単位なので、同じ限界がある見込み（未検証）。
- 補正（余計な遅延を差し引く）や、短い遅延だけ busy-wait で待つ方式を設計で用意するが、**精度は実測で確かめるまで保証しない**。

## 設計への反映

- 遅延の演出は 3 通りを `NetworkModel` の方式として持つ。
  1. **中間サーバ（アプリ内蔵）**: 方向ごとの遅延 + ジッター。可搬・接続ごとに設定可。**数 ms 以上のみ**使う。
  2. **`tc netem`（カーネル）**: 高精度。root（`CAP_NET_ADMIN`）が必要で、同一インターフェースの他の通信にも効く。**この環境には `tc` が無く未検証**。同一 AZ のような短い遅延はこちら。
  3. **実環境（AWS）で測る**: 最終的な確認。ECS → Proxy → Aurora の各区間の実 RTT は、ping / TCP の接続時間 / アプリの計測から実測値をプロファイルに入れる。
- 区間ごとに別の遅延を設定できる: `ECS → Proxy`（アプリ側）と `Proxy → Aurora`（DB 側）。
- 遅延の入力は `固定 + ジッター`（一様 / 対数正規で長い裾）。接続確立の遅延（TLS 含む往復の数）も別に持つ。
- **遅延の既定値は仮置き**（同一 AZ / 別 AZ / 別リージョンの 3 プリセット）。AWS の実測値ではないので、ユーザーの環境の実測で必ず置き換える。
- 試算に `1 ループの時間 = Σ(クエリ) × (RTT + 実行時間)`、`必要な接続数 = ループ/秒 × 1 ループの時間` を加える。
- 測定の精度警告: 設定した遅延と、実際に計測した RTT（空クエリの往復）を並べて表示し、**差が大きければ「演出が不正確」と警告**する。

## 保証しない範囲・未検証

- 1 回きり・10 秒の測定。PostgreSQL のみ（MySQL は未実施）。
- 実際の AWS の RTT・Proxy の追加遅延は未確認。
- 帯域・パケット損失・輻輳の演出は未実装（TCP の再送による遅延は別途）。
