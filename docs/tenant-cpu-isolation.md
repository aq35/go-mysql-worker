# 2 vCPU をテナント単位で分離したら、どこまで耐えるか

**結論**: 2 vCPU の DB は、100 行×100 行の JOIN を **1 秒ごとにポーリングする約 2,400 テナント**まで持つ。
分割しても**総量の天井はほぼ同じ**（CPU が先に尽きる）。変わるのは **余裕があるときの遅延の裾** と **巻き込まれる範囲**。
分割は「速くする」手段ではなく、「ノイジーネイバーの被害範囲を 1/k に絞る」手段。

実装は [scripts/tenant-cpu-lab](../scripts/tenant-cpu-lab)、生データは [docs/results/tenant-cpu-lab](results/tenant-cpu-lab)。

## 測定条件

| | |
| --- | --- |
| DB | PostgreSQL 16.15（`fsync=off`・autovacuum 無効・shared_buffers 256MB / インスタンス） |
| 「2 vCPU」の作り方 | DB をコア 0,1 に固定し、cgroup v1 `cfs_quota` で **合計が常に 2000m**（k=1: 2000m ×1 / k=2: 1000m ×2 / k=4: 500m ×4 / k=8: 250m ×8） |
| 負荷側 | pgbench をコア 2,3 に固定。`-R N`（N テナント × 1 回/秒、到着はランダム）。遅延は**予定時刻から**数える（待ち行列を含む） |
| データ | テナントごとに A 100 行（6 列）・B 100 行（3 列）。主キー `(tenant_id, id)`。1 回の取得 = A と B の JOIN 1 回で 100 行返す |
| テナント割り当て | k 個の DB に均等。pgbench は DB ごとに起動 |
| 1 点あたり | 12 秒・1 回きり（ウォームアップなし）。表の p95 / p99 は **DB ごとの最悪値** |
| 機材 | Intel Xeon 2.1GHz・4 コア・16GB（コンテナ）。クライアントは同一ホストの 127.0.0.1 |

絶対値はマシンで変わる。**1 クエリ ≈ 0.75ms の CPU（接続・pgbench 含む）という桁**と、**CPU が尽きる点で崩れる形**を見る。

## 1. どこまで耐えるか（テナント数 = qps）

遅延 p95 [ms]（`*` は DB の CPU が 189% 以上に張り付いた点）

| テナント数 | k=1 共有 2000m | k=2 1000m×2 | k=4 500m×4 | k=8 250m×8 |
| --- | --- | --- | --- | --- |
| 1,000 | 2.6 | 2.8 | 3.0 | 3.3 |
| 2,000 | **4.8** | 13.0 | 11.7 | 10.3 |
| 2,200 | 8.8 | 9.9 | 38.8 | 136 |
| 2,400 | 10.1 | 124 | 67 | 97 |
| 2,600 | 161 * | 1,277 * | 461 * | 84 * |
| 3,000 | 240 * | 1,117 * | 887 * | 698 * |
| 4,000 | 3,376 * | 3,766 * | 3,754 * | 3,804 * |

- **崩壊点は分割しても 2,400〜2,600 付近で同じ**（k=8 だけ 2,600 は p95 84ms で粘り、2,800 で 1.5 秒に崩れる）。
  CPU 合計 200% の 9 割を使う点で止まる。崩壊後の達成 qps も 2,600〜3,400 に頭打ち（総量は分割で増えも減りもしない）。
- **崩壊の手前の質は分割で落ちる。** 2,000 テナント（CPU ≈ 75%）で p95 は共有 4.8ms → 分割 10〜13ms、p99 は 21ms → 38〜42ms。
  スライスが小さいほど、確率的な偏り（同じスライスに同時に来る）を他のスライスの空きで吸収できない。
  さらに `cfs_quota` のスロットル（k=8 は 2,600 で 536 回）が裾を伸ばす。
- 目安: **k=1 は 2,400 まで p95 10ms 以内、k=2 は 2,200 まで、k=4・k=8 は 2,000 まで**（p95 ≈ 10〜13ms）。

つまり「各テナントに CPU を取り分ける」ほど、同じ総 CPU で安全に使える割合（使用率）は下がる。
共有なら 85〜90% まで使えるが、8 分割では 75% が上限に近い。

## 2. ノイジーネイバー（通常 1,500 テナント + 重い 1 テナント）

重いテナントは、50 人分のデータ（5,000 行×5,000 行）を JOIN・集計するバッチ（2 並列・流しっぱなし）。
バッチ 1 回の CPU は単独で約 9〜10ms。重いテナントは DB d0 に載る。通常テナントの p95 [ms]:

| 構成 | 重いバッチなし | 重いバッチあり: d0（同居） | 重いバッチあり: 他の DB（最悪） | 巻き込まれたテナント |
| --- | --- | --- | --- | --- |
| k=1 共有 2000m | 3.3 | **12.9** | （同じ DB） | **全員** |
| k=2 1000m×2 | 3.3 | 45 | **4.6** | 1/2 |
| k=4 500m×4 | 3.7 | 73 | **4.5** | 1/4 |
| k=8 250m×8 | 4.1 | 179 | **3.9** | 1/8 |

- 分割すると、**重いテナントと別の DB にいるテナントはほぼ無傷**（p95 4〜5ms、無負荷時の 3〜4ms とほぼ同じ）。
- 代わりに、**同居したテナントの被害は大きくなる**（12.9 → 45 → 73 → 179ms）。小さい枠はバッチに食われやすい。
- 共有では全員が少しずつ遅くなるが、境界の外には出ない。分割は「被害を局所に閉じ込めて、その局所を重くする」。

## 3. どう使うか

- **総量が足りないなら分割しても増えない。** 2,400 テナントを超えるなら、DB を大きくするか、ポーリング頻度・クエリ数を減らす（[cache](cache.md) / [fanout](fanout.md)）。
- **ノイジーネイバーが心配なら、重いテナントだけ別枠に隔離する**のが効率的。全員を均等に k 分割すると、
  通常時の余裕（使用率の上限）を払うわりに、効くのは重いテナントが 1 つでもいる場合だけ。
- 分割数は「重いテナントの出現率」と「許容できる遅延の裾」で決める。8 分割（250m）は 2,000 テナントでも p99 が 40ms に伸びる。

## 保証しない範囲・未検証

- **MySQL は未測定**。この環境に mysqld が無い（Docker も無い）。PostgreSQL のみ。MySQL との比較は未実施。
- 1 点 12 秒・1 回きり。ウォームアップなし（最小の 500 テナントの点は CPU が割高 = コールドキャッシュ）。点間の揺れは数十 % ありうる。
  特に k=4 の 2,200 / 2,400、k=8 の 2,600 は p95 の並びが逆転している（スロットルの偶然）。**傾向を見る表**。
- **テナントごとに DB（またはインスタンス）を 1 つ持つ「真のテナント単位」（k = テナント数）は測っていない。**
  CPU 上限は 1 ミリコア単位まで設定できるが、先に効くのはプロセス・メモリ・接続数のはず。インスタンスあたりのメモリは未計測。
- 重いバッチの競合時、DB の CPU が 199% まで膨らんだ内訳は**未確認**（通常側 ≈ 112% + バッチ単独コストでは 130% 弱にしかならない）。
  ロック競合・コンテキストスイッチ・並列クエリのワーカー起動のいずれかと推測しているが、検証していない。
- `cfs_quota` は上限であって予約ではない。ECS/Fargate の vCPU や RDS の vCPU（ハイパースレッド）とは挙動が違う。
- 実験 A〜E・G・H（JOIN 数・インデックス・1 万行・一括取得・キャッシュ）は今回やっていない。
  今回は F（実行頻度）と「テナント単位の分離」のみ。
