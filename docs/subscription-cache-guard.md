# サブスクリプションをキャッシュ化したら、リポジトリ層のガードが効かなくなった（EXP-64）

**バグシナリオ**

1. 状態の配信を **サブスクリプション**（gqlgen / SSE）にした。最初は購読者1人ごとに DB を引いていた。
2. 購読者が増えて接続プールが埋まった。**接続数を抑えるため、キャッシュ対応した**
   （バックグラウンドで1回だけ読み、購読者はキャッシュから読む）。
3. **DB の ORM（`repo.Scope`）が効かなくなり、テナントがガードされなくなった。**
   他テナントのロボットの状態が配信された。エラーはどこにも出なかった。

実装は [internal/subguardlab](../internal/subguardlab)、receipt は
[docs/results/exp-64](results/exp-64/exp-64-subscription-cache-guard-bypass.md)。

## なぜガードが外れるのか

ガード（`repo.Scope` の `:tenant` 束縛・`sqllint` の rawdb 禁止）は **「DB を通る経路」にしか無い**。
キャッシュ化は、その経路を2か所で迂回する。

```
修正前:  購読者(ctx=tenantB) ─► repo.Tenant(B).QueryRow(... tenant_id=:tenant ...) ─► DB
                                 ▲ ここでテナントが強制される（ガード）

事故:    poller(ctx=Background) ─► repo.Unscoped("cache warm-up") ─► 全テナントの行 ─► map[robotID]
         購読者(ctx=tenantB) ────────────────────────────────────────► map[robotID] を読むだけ
                                 ▲ ①テナントが無いので逃げ道を使う    ▲ ②DB を通らないのでガードが一度も走らない
```

- **① 読み込み側**: バックグラウンドの poller は「リクエストの主体」を持たない（`context.Background()`）。
  `repo.Tenant(t)` に渡すテナントが無いので、`Unscoped`（や生の `*sql.DB`）で **全テナントを1本で** 読んでしまう。
  接続を減らす目的にも合ってしまうので、レビューで違和感が出にくい。
- **② 読み出し側**: キャッシュのキーが `robot_id` だけ。購読者は自分の ctx（テナント）を見せずに値を取る。
  `robot_id` はテナント内の連番なので、**テナントを跨ぐと同じ ID が普通にある**。

## 結果（2 テナント・購読者 80・poll 20 回・プール既定 20 本）

tenantA は robot 1..100、tenantB は robot 1..60（**1..60 は両方にある**）。
購読者は A 40 人・B 30 人（自分の robot）・B 10 人（**B に無い ID 61..97 を指定**＝総当たり・取り違え）。

| 方式 | DB 問い合わせ | 同時接続ピーク | プール待ち | 他テナントの行を配った | うち ID 衝突 | うち B に無い ID | エラー |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ① 購読者ごとに `repo.Tenant(t)`（修正前） | 1600 | **20（上限）** | **1198** | **0** | 0 | 0 | 0 |
| ② `Unscoped` で全テナント → `map[robotID]`（★事故） | **20** | 1 | 0 | **680 / 1600（43%）** | 480 | 200 | **0** |
| ③ テナントごとに `repo.Tenant(t)` → `tenantcache(tenant, id)`（修正後） | **40** | 1 | 0 | **0** | 0 | 0 | 0 |

- ①はガードが効いていて漏れは 0。ただし問い合わせは **購読者数 × poll**。同時接続はプール上限 20 に張り付き、
  **約 1200 回（1198）待たされた**。ここがキャッシュ化したくなる理由（[EXP-5](pool-saturation.md) / [EXP-60](connection-budget.md)）。
- ②は問い合わせが poll 1本に減り、接続の問題は消えた。**その代わり配信の 43% が他テナントの行**。
  - **ID 衝突（480）**: 読み込み順で後の tenantB が `map[1..60]` を上書きし、**A の購読者に B の値**が届いた。
  - **B に無い ID（200）**: B の購読者が ID 61..97 を指定すると、**A の行がそのまま返った**（認可の素通り）。
  - **エラーは 0**。DB を通らないので、`ErrMissingTenant` も行数検査も一度も走らない。
    残る痕跡は **`Stats().CrossTenant`（`Unscoped` の回数）= 20** だけ。
- ③は問い合わせ **テナント数 × poll = 40**（購読者数に依らない）、同時接続 1 のまま **漏れ 0**。
  B に無い ID は「無い」（not_found 200）と返り、ctx にテナントが無いと `ErrNoTenant` で引けない。

## 修正（③の形）

1. **読み込みはテナントごとに `repo.Tenant(t)` で1本**。「購読者が居るテナント」の一覧で回す。
   全テナントを1本にまとめない（まとめた瞬間にガードの外に出る）。本数はテナント数で、購読者数ではない。
   テナント数が多いなら hub 共有と版で差分（[EXP-38](sse-fan-in.md) / [EXP-52](subscription-design.md)）で畳む。
2. **キャッシュのキーは `(tenant, id)` の2段**。`tenantcache.Cache` のように **tenant 無しでは引けない型**にする
   （`repo.Scope` が `:tenant` を必須にするのと同じ「構造で禁じる」）。
3. **購読者のテナントは ctx から**（認証ミドルウェアが載せた値）。購読引数・変数からは取らない（[EXP-24](graphql.md)）。
   ctx に無ければエラー。黙って全テナントにしない。
4. **自テナントに無い ID は「無い」**。他テナントや全体キャッシュへフォールバックしない。
5. **`Unscoped` を業務経路で使ったら設計を疑う**。`repo.Stats().CrossTenant` を監視し、
   サブスクリプション/キャッシュの経路で 0 でなければアラートにする（②はここでしか見えなかった）。

## レビューで見るところ

| 探すもの | 何が起きるか |
| --- | --- |
| バックグラウンド goroutine / poller での `Unscoped` や生の `*sql.DB` | テナントが無いから逃げ道を使った。全テナントの行がキャッシュに入る |
| キャッシュのキーが `id` だけ（`map[int64]T`、Redis の `robot:{id}`） | テナント内連番の ID がテナント間で衝突して値が入れ替わる |
| キャッシュの `Get(id)` が ctx（テナント）を受け取らない | 読み出しが DB を通らないのでガードが走らない。他テナントの ID で行が返る |
| 「キャッシュに無ければ全体から探す」フォールバック | 自テナントに無い ID で他テナントの行が返る |
| 無効化イベント（pub/sub）のメッセージにテナントが無い | 他テナントの購読者へ誤配信する（本実験外・[EXP-43](sse-fan-in.md) の経路で同型） |

## 保証しない範囲・未検証

- キャッシュはメモリ `map` で測った。Redis 等のプロセス外キャッシュでも「キーにテナントが無い・読み出しが repo を通らない」
  なら同型だが、実測はしていない。
- どちらのテナントの値が勝つかは読み込み順（`ORDER BY tenant_id`）で決まる。順序が変わると漏れる側が入れ替わるだけ。
- 無効化イベントにテナントが無い場合の誤配信は本実験外。
- テナント数が非常に多い場合のテナントごと poll の本数は、本実験では 2 テナントでしか測っていない。
