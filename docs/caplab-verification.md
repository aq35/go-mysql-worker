# caplab の検証記録（PostgreSQL 16.15 / MySQL 8.0.46・ローカル）

[caplab](../caplab) の機能を、ローカルの 2 つのエンジンで確かめた結果。**絶対値はこの環境のもの**（4 コアの VM、DB を cgroup で 2 vCPU 相当に制限、負荷側は別の 2 コアに固定）。傾向と、どこで壊れたかを見る。
環境の作り方は [scripts/tenant-cpu-lab](../scripts/tenant-cpu-lab)（`lib.sh` の `pg_start` / `my_start`）。いずれも各 1 回の測定。

## 1. クエリの送り方（校正、8 同時、CPU/回 と p50）

| エンジン | 送り方 | `sites_pk` | `readings_by_devices` | `tree_join` |
| --- | --- | --- | --- | --- |
| PostgreSQL | テキスト | 0.047ms / 0.23ms | 0.054ms / 0.31ms | 0.193ms / 0.73ms |
| | プリペア（再利用） | 0.032ms / 0.31ms | 0.036ms / 0.39ms | 0.084ms / 0.72ms |
| | 毎回プリペア | 0.086ms / 0.49ms | 0.113ms / 0.58ms | 0.242ms / 1.05ms |
| MySQL | テキスト | 0.041ms / 0.26ms | 0.095ms / 0.35ms | 0.197ms / 0.81ms |
| | プリペア（再利用） | 0.038ms / 0.34ms | 0.082ms / 0.35ms | 0.185ms / 0.94ms |
| | 毎回プリペア | 0.083ms / 0.66ms | 0.133ms / 0.69ms | 0.245ms / 1.22ms |

**毎回プリペア（Go の `go-sql-driver/mysql` が引数つきクエリで既定でやる形）は、テキストの約 2 倍の CPU と遅延**（両エンジンとも）。往復が 3 回になるため。

## 2. 書き込み（10 秒、1 テナント 15 qps × 60 テナント、更新 2 本 / ループ）

| | 読み取りの実行 p50 | 書き込みの実行 p50 | 書き込みの p95 |
| --- | --- | --- | --- |
| PostgreSQL（`fsync=off`） | 0.52ms | 0.41〜0.54ms | 0.7〜0.8ms |
| MySQL（`flush_log_at_trx_commit=1`） | 0.45ms | **0.97〜1.18ms** | 1.6〜1.8ms |

耐久性設定が緩い環境では書き込みが読み取りと同じ速さに出るため、アプリが設定値を読んで注記する。ホットロウ（tenant の Zipf 1.5 + 1 行に集中）: MySQL のロック待ちが 1 → 274 に増えたが p95 は 9.7 → 9.8ms でほぼ変わらず（短いトランザクション）。

## 3. 障害注入（実行 5 秒目に接続を強制切断、web 5 qps × 60）

| | 切断数 | 回復まで | エラー（再試行あり / なし） |
| --- | --- | --- | --- |
| PostgreSQL | 6〜7 本 | 2 秒 | 2 件 / 6 件 |
| MySQL | 6〜7 本 | 2 秒 | 1 件 / 6 件 |

再試行は新しい接続で最大 3 回。1 回だと、死んだ接続が複数残っているため足りないことがあった。

## 4. 遅延の演出（SELECT 1 の往復 p50、設定 RTT との差）

| 設定 RTT | PostgreSQL | MySQL |
| --- | --- | --- |
| 0.2ms | 0.44ms（+0.13） | 0.43ms（+0.14） |
| 0.5ms | 0.79ms（+0.21） | 0.87ms（+0.27） |
| 1ms | 1.34ms（+0.25） | 1.36ms（+0.27） |
| 2ms | 2.39ms（+0.29） | 2.44ms（+0.34） |
| 5ms | 5.49ms（+0.40） | 5.55ms（+0.46） |

（括弧内は `計測 − 設定 − 直結の往復（約 0.1ms）`＝中間サーバが足した分。）最後の 0.2〜2.5ms を空回りで待つ方式で、タイマーの刻み（約 1ms）の影響を避けた。以前の Python 試作は 1 往復あたり約 2ms の上乗せがあった（[network-latency-emulation](network-latency-emulation.md)）。

1 ループ（親→子→孫、7 クエリ）の遅延は、RTT 1ms で 11.1ms、2ms で 17.8ms、5ms で 38.6ms（≈ 3.6ms + 7 × RTT）。

**注意（MySQL）**: `mysql_async` は既定で、ローカル接続のとき Unix ソケットに切り替える（`prefer_socket`）。これだと遅延プロキシを迂回する。本アプリは TCP に固定している。

## 5. Proxy の 3 層観察（PgBouncer・トランザクション単位・プール 5）

アプリのプール 30 → Proxy 経由で DB 側 5 本（アプリ → Proxy 31、Proxy → DB は実行中 2・待機 5）。

## 6. 負荷の形・SSE の一斉接続

| | PostgreSQL | MySQL |
| --- | --- | --- |
| スパイク（4〜7 秒に 6 倍）の p95 | 3.0ms のまま | 16 → 28 → 34 → 60 → 70ms |
| SSE 60 テナント × 50 接続（プール 10）の初期取得 p50 / p99 | 177ms / 229ms | **3,103ms / 4,127ms**（原因未特定。README の「限界」） |
| 同上、テナントごとに 1 回へまとめる | 26ms / 28ms | 70ms / 91ms |

まとめる（singleflight）と、3,000 回の初期取得が 60 回になる（PostgreSQL・MySQL とも）。

## 7. 掃引・繰り返し・ソーク（PostgreSQL）

- 掃引（web 3 qps/テナントの N+1、各 8 秒）: 50 → 1,101 qps（CPU 7%）、100 → 2,072（11%）、200 → 4,219（20%）、300 → 6,352（28%・**負荷側が先に詰まる**と判定し、安全上限の計算から除外）。
- 繰り返し 3 回: p95 5.29 ± 0.20ms（CV 3.7%）、qps 2,103 ± 67（CV 3.2%）。
- ソーク 36 秒: 計測の前半 → 後半で p95 +25%、DB の接続数 +53%（プールが必要に応じて増えた分。リークとは限らない）をドリフトとして検出。

## 8. 取り込み・診断

- DDL: 外部キーから親子を取り、無ければ `xxx_id` の列名から推定して警告。
- クエリ: `pg_stat_statements` / `performance_schema` / 貼り付け。集計期間を省略すると、統計の累積期間（稼働時間）を使う。取り込んだクエリを実行できた（値は乱数のため、返る行は少ない）。
- EXPLAIN: `tenant_id` を先頭にした主キー `(tenant_id, id)` があれば、外部キーのインデックスを外しても子の一覧は全件走査にならない（主キーの範囲検索になる）。`WHERE c1 = 3` のような列は全件走査と検出。
- 外部メトリクス（CSV）: CPU 31% を取り込むと、結論の CPU と安全上限（419 → 178 テナント）が計算し直された。

## 9. TLS

PostgreSQL / MySQL とも: 暗号化なし → `暗号化していません`、暗号化のみ（証明書は検証しない）→ `TLS で暗号化されています`、検証あり → 自己署名を拒否（接続失敗）。負荷実行も TLS で通った。
`mysql_async`（rustls）と `tokio-postgres-rustls` が別々に rustls を使うため、起動時に暗号プロバイダ（ring）を明示しないとパニックする。
