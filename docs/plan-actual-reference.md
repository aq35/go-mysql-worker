# 予定と実績を分けたときの参照（ID 参照・名前のスナップショット・入れる時期）

予定（`cmd_schedule`）と実績（`cmd_result`）を分け、実績から予定を ID で参照する設計の判断を残す。
3つの表の定義は [scheduling](scheduling.md)（EXP-12）、スキーマは
[internal/cadencelab/schema.sql](../internal/cadencelab/schema.sql)。

> この文書は**設計判断の記録**で、実験で測ったものではない（末尾「未検証」）。

## 1. ID で参照するのは正しい。ただし「物理削除しない」だけでは足りない

壊れやすいのは削除より**更新**のほう。

- **予定は UPDATE される**（時刻の変更、対象ロボットの付け替え、パラメータの修正、`enabled=0`）。
  実績が `schedule_id` しか持たないと、JOIN で見えるのは**今の予定**で、実行したときの予定ではない。
  - 10:00 に実行した実績が、予定を 11:00 に変えると「11:00 の予定の実績」に見える。
  - 対象を A から B に付け替えると、A で走った実績が B の実績に見える。
- **周期の予定（`interval`）は1行から何回も実行される**。`schedule_id` だけでは何回目の実績か区別できない。

実績が過去の事実を正しく示すには、参照先の行が**変わらない**ことが要る。行が残っているだけでは足りない。

### このリポジトリの形: 予定 → 命令 → 実績

```
cmd_schedule（予定・更新される）
   │ next_run_at が来たら1件生む（その時点の値をコピーする）
   ▼
cmd_command（命令・1回の実行。robot_id / type / payload / scheduled_for を固定）
   │ command_id で参照
   ▼
cmd_result（実績・追記のみ。PK = tenant_id, command_id, observed_at）
```

- 実績が参照するのは**命令**。命令は生成した瞬間の予定のコピーで、あとから変えない。
  予定をいくら UPDATE しても、過去の実績には影響しない。
- 「どの予定から生まれたか」を追いたいなら、命令に `schedule_id` を持たせる。
- 命令の表を作らない場合は、**実績の行に実行時点の値**（予定時刻・対象・パラメータ）を一緒に持たせる。

### 参照と削除の約束

- **参照はテナント込み**: `(tenant_id, schedule_id)` で持ち、JOIN にも `tenant_id` を入れる。
  ID だけで JOIN すると、テナント内連番の ID が衝突したときに他テナントの行を拾う
  （[tenant-scope](tenant-scope.md) EXP-58 / [subscription-cache-guard](subscription-cache-guard.md) EXP-64 と同型）。
- **予定は消さずに止める**（`enabled=0`）。「消さない」は人の注意ではなく仕組みで守る。
  - 外部キー `ON DELETE RESTRICT` で守れる。ただし **MySQL のパーティション表には外部キーを張れない**ので、
    実績を `DROP PARTITION` で捨てる設計（[retention](retention.md) EXP-48）とは両立しない。
  - 外部キーを使わないなら、予定への DELETE をアプリ（repository 層）で禁止する。
- **いつかは消える前提にする**: 保持期間を過ぎた実績は消える。消す順番は「実績 → 予定」。
  実績のほうが長生きしうるなら、なおさら実績に値のコピーを持たせる。

| 状況 | 判定 |
| --- | --- |
| 実績が予定の ID だけを持ち、予定を UPDATE する | ✗ 過去の実績の意味が変わる |
| 実績が予定の ID だけを持ち、周期実行がある | ✗ どの回の実績か分からない |
| 実績が命令（実行1回）の ID を持ち、命令は変えない | ◯ |
| 実績に実行時点の値も持たせる | ◯（命令の表が無いならこれ） |
| 参照・JOIN が `tenant_id` 込み | 必須 |

## 2. 名前（論理名）も実績に持たせるか

**持たせてよい。ただしキーではなく「実行した時点の名前」の記録として。** ID はキー、名前は表示と記録用。

| 画面・帳票に出したい名前 | どうするか |
| --- | --- |
| 実行した時点の名前（監査・報告書・請求など、過去の事実） | 実績に名前をコピーして持たせる |
| 今の名前（改名したら過去の実績も新しい名前で見せたい） | コピーしない。ID で JOIN して今の名前を引く |
| 両方ありうる | 両方持つ（コピーした名前＋ID で今の名前） |

注文明細が商品名と単価を注文時点の値で持つのと同じ考え方。名前も予定・ロボットの属性なので、改名されると
過去の実績の見え方が変わる（1. と同じ問題）。

### 持たせるときの約束

1. **キーにしない**。名前は一意ではない（テナント内でも重複しうる。テナントを跨げば必ず重複する）。
   WHERE・JOIN・UNIQUE は `(tenant_id, id)` で行い、名前で引かない。
2. **コピーした値だと列名で分かるようにする**（例: `schedule_name_at_run` / `robot_name_snapshot`）。
   `schedule_name` だけだと、誰かが「元の表とずれている」と UPDATE で揃えてしまう。ずれているのは仕様。
3. **書くのは実績を作るときの1回だけ**。改名に追従させる UPDATE は書かない（実績は追記のみのまま）。
4. **参照先が消えても読める**。予定やロボットの行が保持期間で消えても、何の実績だったか分かる。
   物理削除への保険にもなる。

### コスト

- 行が少し太くなる。utf8mb4 の `VARCHAR(64)` で最大 256B（[charset](charset.md) EXP-57）。
  追記のみの実績表なら、まず問題にならない。
- 名前に索引は要らない（検索に使わない）。名前で検索・集計したくなったら、それは表示用の名前ではなく
  **分類のコード**が欲しいサイン。別の列として持つ。

### 補足: 設計書の「論理名」（列の和名）

それも付ける。`COMMENT '予定名（実行時点のスナップショット）'` のように列のコメントに入れれば、
DDL と設計書がずれにくい。コストはほぼゼロ。

## 3. 名前のスナップショットは後から入れてもよいか

**後でもよい。ただし後回しにできるのは列の追加だけで、データは後から取り戻せない。**

- **後からでも簡単**: NULL を許す列の追加は expand/contract の expand で安全
  （[zero-downtime-migration](zero-downtime-migration.md) EXP-32）。MySQL 8.0 なら `ALGORITHM=INSTANT` で済む場合が多い
  （版と操作で INPLACE になることがあるので、本番と同じ版で確かめる）。書き込み側は実績を作る処理に1行足すだけ。
- **後から取り戻せない**: 実行した時点の名前は、その時点でしか取れない。列を足す前に改名があると、
  それより前の実績の「当時の名前」は永久に失われる。後から埋められるのは**今の名前**だけで、当時の事実ではない。

### 後回しにしてよい条件（どれかに当てはまれば）

- まだ改名ができない（画面や API に名前を変える操作が無い）
- 実行時点の名前が要る帳票・監査の要件がまだ無い
- 名前の変更履歴（監査ログなど）を別に残している。これがあれば、後から「実行時刻の時点の名前」を正確に復元できる

逆に、改名がすでにできて、当時の名前を見せる要件が来そうなら、今入れたほうが安上がり。

### 後回しにするなら、今やっておくこと

1. 参照は `(tenant_id, id)` で持ち、参照先は物理削除しない（1. のとおり）。
2. 後から足すときは、列名で「当時の名前」だと分かるようにする（`*_at_run`）。
3. 足す前の実績は **NULL のまま**にしておく（NULL＝不明）。今の名前で埋めるなら、当時の名前と区別できる印を付ける
   （例: `name_source = 'backfill'`）。今の名前で黙って埋めると、当時の事実と区別がつかなくなる。

**段階の目安**: 今は ID とテナントで正しく参照して削除しないところまで。改名の機能か帳票の要件が出る**前に**、
当時の名前の列を足す。改名がすでにできるなら、入れるのは早いほど失うものが少ない。

## 保証しない範囲・未検証
